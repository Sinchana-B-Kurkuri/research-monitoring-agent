Relevance-Gated Agentic Workflow for Autonomous Research Monitoring
Implementation Roadmap and Development Plan (Final)
Master implementation plan derived from the project proposal, the agreed development roadmap, and a full review of phase dependencies, evaluation design, pilot timing, and deployment constraints.
Notation. [P] = specified in the project proposal. [R] = recommendation or inference added for implementation (change it only with a recorded reason in docs/decisions.md). Day N = day of the planned build of about 28–30 days.
1. Project Implementation Overview
This document defines the step-by-step implementation plan for the Relevance-Gated Agentic Workflow for Autonomous Research Monitoring: an autonomous system that discovers research papers, evaluates their relevance to a user’s interests, routes papers through a three-way relevance gate, requests human review for borderline cases, generates interest-framed summaries for papers that clear the gate, collects feedback, and adapts future routing using preference memory.
The implementation follows the proposed explicit Python state-machine architecture [P] rather than a general-purpose multi-agent framework. The agentic behaviour comes from autonomous routing and adaptation decisions that are recorded and auditable.

1.2 Implementation Principles
Build incrementally: prove the smallest working pipeline before adding databases, UI, LLMs, and deployment.
Use Antigravity as an AI engineering assistant, not as an autonomous replacement for project understanding.
Keep the explicit state-machine design and avoid unnecessary frameworks such as LangChain, CrewAI, or AutoGen. [P]
Persist decisions and statuses so asynchronous human review does not block the monitoring pipeline.
Deploy a cold-start version early so real feedback can accumulate while the learning components are being built. [R]
Express routing thresholds as percentiles of a fixed reference sample, so they remain valid when the interest vector changes and transfer across users. [R]
Calibrate thresholds on labelled development data and report only on a frozen test split. [R]
Keep reviewer feedback and end-user feedback as separate signals in storage; combine them only through one explicit rule. [P][R]
Use replay mode to simulate repeated monitoring cycles without waiting for real weeks to pass, and keep replay/simulated data separate from live pilot data. [R]
Log enough information to reproduce routing decisions, model versions, experiments, and paper results.
Keep secrets and data files out of Git from the first commit.

2.1 Asynchronous Human Review
Human review cannot be a blocking function inside a monitoring run. A borderline paper is persisted as a review task with status PENDING_REVIEW. The cycle finishes; the reviewer decides later. A resume step then moves ACCEPTED papers to SUMMARIZE_PENDING (and on to the digest), while REJECTED and EXPIRED papers end in terminal statuses. The resume step is idempotent and can be re-run safely.
2.2 Replay Mode
Replay mode processes historical papers as if they arrived in separate monitoring cycles (for example week by week) using the cycle parameter as_of_date. It uses precomputed embeddings, so no embedding model call is needed.
Replay runs locally against the full corpus. Replay cycles are tagged mode = replay, and simulated users are tagged is_simulated = true, so they can never be confused with live pilot data.
=== LINE 137 ===
Replay can optionally use a simulated-feedback oracle (the labelled development pool, Section 8.4) to react to delivered papers and decide borderline papers. This is how repeated cycles, feedback accumulation, retraining, and changed routing are demonstrated without waiting for real time.
2.3 Shared versus Per-User Processing
Global (once per paper): ingestion, preprocessing, embedding. Embeddings are L2-normalized at storage time, so a dot product equals cosine similarity.
Per user: scoring, routing, review, digest, feedback, interest vectors, and models. All per-user tables are keyed by user_id.
The embed node has two behaviours: in replay mode it looks up stored embeddings; in live mode it computes embeddings for newly fetched papers.
At 50–100k papers, exact vector search is sufficient. No vector index is required, and scoring all papers against one vector is a trivial NumPy operation. Postgres/pgvector [P] is used for storage and convenient queries.
2.4 Runtime Architecture and Deployment Constraints
Hosted free tiers are small, and the embedding model requires PyTorch. The deployed system is therefore split into three runtime pieces. [R]

7. AI/ML Decision Logic
7.1 Interest Vector and Scoring
Each user has an active interest vector v. Version 0 is the embedded seed paragraph. Later versions are Rocchio centroids (Section 7.4). The routing score before a classifier exists is s = cosine(paper_embedding, v). Because embeddings are normalized, this is a dot product.
7.2 Percentile Thresholds and Calibration (Cold Start)
For the active vector, score the 5,000 reference papers. t_high is the P_high percentile and t_low is the P_low percentile of those scores. Thresholds are therefore recomputed automatically whenever the vector changes. [R]
Routing: s ≥ t_high → HIGH; s ≤ t_low → LOW; otherwise BORDERLINE. [P] (threshold-based cold start)
Provisional levels before calibration: P_high = 98, P_low = 90.
Calibration objective (development split, weighted): choose the smallest P_high whose HIGH precision is at least 0.80; choose the largest P_low whose LOW miss rate (fraction of relevant papers routed LOW) is at most 10%, aiming for 5%; require P_low < P_high. If a target is unattainable, take the best achievable value and report it. Always report the BORDERLINE share and composition.
Pilot users start from the developer’s calibrated levels (percentile levels transfer across users better than raw cosine values), sanity-checked on their calibration labels.
Known trade-off: percentile thresholds fix the share of papers routed to each class for a stream similar to the reference sample. Report routed shares as a consequence of the chosen levels, with a sensitivity analysis (for example P_high in {95, 98, 99}), not as a finding in itself.
7.3 Feedback Rules and Effective Labels
Two sources are stored separately: reviewer decisions on borderline papers and user reactions to delivered papers. [P] Raw events are append-only.
Training, centroid updates, and cross-validation use one effective label per (user, paper): the most recent user like/dislike if one exists; otherwise the reviewer decision; skip and expired tasks give no label. [R]
Audit-sample labels (optional) are reviewer-source labels flagged is_audit and may be included or excluded in analyses.
Ablations (E3) derive user-only, reviewer-only, and combined label sets from the raw events with the same rule.
Pilot onboarding ratings live in validation_labels and never enter training_labels.
7.4 Interest Vector Update (Rocchio-Style)
c = normalize( alpha*c0 + beta*mean(effective positives) - gamma*mean(effective negatives) )
alpha = 1.0, beta = 0.75, gamma = 0.25   (tunable defaults)
c0 is the seed vector. The centroid is recomputed from all effective labels at each update, so it is reproducible from built_from_max_event_id.
First update at 10 effective labels with at least 3 positives; then after every 25 new effective labels.
A new centroid becomes the routing vector from the next cycle, and percentile thresholds are recomputed under it (Section 7.2).
7.5 Classifier Phase
p = P(relevant | paper_embedding)
Eligibility: at least 30 effective labels (50 preferred), at least 8 positives and 8 negatives. Retrain after every 25 new effective labels.
Model: L2-regularized logistic regression, class_weight = balanced, C from {0.1, 0.3, 1.0} by inner cross-validation.
Promotion guard (Phase 11): out-of-fold ROC-AUC at least 0.65 and at least the cosine-to-current-centroid AUC on the same labels plus 0.02.
Routing in classifier mode: p ≥ p_high → HIGH; p ≤ p_low → LOW; otherwise BORDERLINE. Start with 0.70/0.30 (provisional) and calibrate with the Section 7.2 objective.
Feedback is biased toward papers the gate already liked (digest items skew positive and discarded papers receive no feedback). Treat out-of-fold results on feedback data as optimistic and rely on the labelled test split for reported performance.
7.6 Review Queue and Caps
BORDERLINE papers are queued for review up to 15 per user per cycle, ordered by score (highest first, recall-oriented).
Overflow papers are logged as DEFERRED_OVERFLOW, receive no label, and are not carried over. Undecided tasks expire after 3 days (REVIEW_EXPIRED) with no label.
The digest is capped at 20 items per cycle; HIGH papers beyond the cap are DEFERRED_OVERFLOW and are not summarized.
7.7 Where Summarization Belongs
Summarization runs only for papers that will appear in the digest: HIGH papers within the cap and review-accepted papers. [P] Reasons: LOW papers are the majority and summarizing them wastes cost and latency (the basis of the LLM-call reduction result); the gate stays cheap, deterministic, and inspectable with no LLM inside the decision; and the summary prompt (abstract + user interests) explains why the paper matches rather than restating the abstract.
7.8 Explanations
Because logistic regression coefficients over 384 embedding dimensions are not human-readable, each decision is explained by the nearest liked/accepted and nearest disliked/rejected papers plus the score or probability, the thresholds used, and the vector/model version. [R]
8. Evaluation Plan
The evaluation must demonstrate not only that papers can be classified, but that gating, human review, and preference learning provide measurable value, with a statistically honest design for a small labelled set.

8.4 Simulated-Feedback Protocols

Oracle: a simulated user likes a delivered paper if its primary label is relevant; a simulated reviewer accepts a borderline paper under the same rule. Optional noise sensitivity may be added.

n values: 0, 10, 20, 30, 50, 75, 100, 150 (up to pool size). For n below the classifier eligibility rule, the system curve uses cosine-to-centroid; the switch point is marked on the plot.

9.3 Viva Explanation of “Agentic”
The system is implemented as an explicit state machine rather than a general-purpose multi-agent framework. Its agentic behaviour arises from autonomous routing decisions: each paper is evaluated and independently routed to automatic processing, human review, or discard, with the reason recorded; uncertain cases are escalated to a human instead of guessed; and subsequent feedback changes the interest vector and model that drive future routing.
